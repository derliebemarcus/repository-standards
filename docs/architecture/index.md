# Architecture

## Purpose

The repository separates normative policy, machine-readable requirements, executable reference
state, generated consumer assets, and implementation-specific provider integration.

## Building blocks

- `standards/` contains immutable versioned specifications.
- `schemas/` describes repository, ticket, sidecar, evidence, and artifact declarations.
- `profiles/` contains machine-readable rules, compatibility pairings, profile requirements, and
  impact mappings.
- `reference/` contains golden declarations, generated ticket templates, AI adapters, fixtures, and
  versioned repository-declaration examples.
- `tools/` validates contracts and derives reference assets.
- `tests/` prevents drift between normative, machine-readable, generated, guidance, and published
  forms.
- `workboard` remains the external ticket-migration and dependency-reconciliation implementation.
- `maintenance` remains the external Jenkins Shared Library, artifact-provenance, bootstrap,
  readiness-provider, and deployment-enforcement implementation.

## Contract flow

```text
versioned normative standards
          |
          v
machine-readable profiles + schemas + compatibility pairing
          |
          v
version-aware validators/generators + reference declarations + sidecars
          |
          v
contract tests -> released-artifact immutability + current guidance consistency
          |
          v
immutable release -> explicitly migrated consumers
```

Implementations consume released artifacts. They do not fetch or reinterpret mutable `main` as their
contract on every operation.

Published contract versions are immutable. A successor specification is additive: it receives its
own normative standard, profile or schema where applicable, and versioned references. Generated
assets may be shared between versions only while their generated bytes and semantics remain valid;
tests protect that invariant.

## Compatibility boundary

Repository declarations are compatibility contracts. The current additive machine-readable pairing
matrix is:

`profiles/repository-standards-compatibility-v10.json`

It preserves every earlier released pairing and contains supported declarations through v11. The
latest supported v11 core pairing selects:

- Ticket Specification v5;
- Development Workflow v8;
- Repository Documentation v2;
- Technology Baseline v1;
- Contract-first Delivery v1; and
- Product/System Readiness v1.

The v11 Web pairing additionally selects Web Application Baseline v3 and Deployment Environments v1
and requires Repository Localization v1. Deployment Environments v2 is independently published and
does not replace the version selected by a compatibility pairing implicitly.

Earlier declarations remain immutable and supported according to their released compatibility
profiles. Unsupported combinations are rejected. Publishing or supporting a newer pairing never
migrates a repository automatically.

The repository's own `.repository-standards.yml` is also a consumer declaration. It may therefore
remain on an earlier supported pairing until an explicit, reviewed self-adoption migration qualifies
the newer contract set.

## Runtime and provider boundaries

Repository-local validation reads selected standards, profiles, schemas, compatibility data,
sidecars, and reference assets. Boilerplate or generated assets are produced from version-specific
inputs and must not silently use a newer contract than the consumer selected.

Ticket migration and dependency writes occur in Workboard rather than this repository. Lifecycle
automation, Jenkins/bootstrap enforcement, artifact-provenance generation, Product/System Readiness
evidence evaluation, and deployment promotion remain Maintenance responsibilities. Repository
Standards publishes portable contracts but does not mutate organization labels, consumer tickets, or
deployed environments merely by releasing a new version.

No runtime service or persistent datastore is required to interpret Repository Standards. Immutable
release identities are the durable distribution boundary.

## Product/System Readiness boundary

Product/System Readiness v1 is selected by declaration v11, but applicability remains independently
authored in `.product-readiness.yml`. A repository type or compatible declaration does not manufacture
a Product/System Subject or current readiness state.

The architecture preserves:

```text
authored intent != derived readiness
target != candidate != assessed != established
deployment != operational proof
PROD != TRL 9
Product Stage != TRL
```

The portable standard defines semantics, schemas, validation boundaries, and evidence contracts.
Productive evidence collection/evaluation and gate activation are provider capabilities and require
their own qualification.

## Branching boundary

Repository declarations select `single` or `integration`. The normal Jenkins Multibranch discovery
filter where specified by the selected workflow is:

```regex
^(main|develop|PR-[0-9]+)$
```

Provider-specific status/check names are adapters around logical contract requirements. They do not
become normative merely because Jenkins, Forgejo Actions, or GitHub uses them.

See `docs/reference/branching-models.md` and `docs/reference/compatibility.md`.

## Web and deployment boundary

Web Application Baseline versions own user-visible web requirements. Deployment Environments
versions own runtime-environment, immutable promotion, artifact release-state, and rollback
semantics. Repository Localization and Repository Environments are separately versioned repository
metadata contracts.

Source revision, artifact release state, and runtime environment remain independent dimensions. A
branch name or environment URL does not prove a release, successful deployment, operational use, or
readiness level.

See `docs/reference/web-application-and-deployment.md`.

## Design-source boundary

Design Source Declaration v1 identifies a repository-owned normative design source without making a
tooling integration such as Penpot-RPC part of that design authority. Contract-first Delivery binds
an exact design artifact/revision where a Design Contract requires it. These responsibilities remain
separate.

## Constraints

The repository MUST remain usable with Python's standard library. Project documentation and prompts
MUST NOT be centralized here. Compatibility with existing provider and consumer integrations MUST be
preserved during explicit migrations.

## Quality requirements

The design prioritizes one source of truth, reproducibility, offline validation, explicit
versioning, additive migration, immutable artifacts, idempotent automation, auditable writes,
revision-bound evidence, and fail-closed behavior without destructive historical rewriting.
