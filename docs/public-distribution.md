# Public Core distribution

The GitHub Repository Standards repository is a generated distribution, not a second canonical repository.

## Source-of-truth model

Forgejo is the single source of truth. GitHub is written only from a qualified canonical revision. There is no reverse or bidirectional synchronization.

External proposals enter through GitHub Issues. Accepted work is implemented and qualified in Forgejo and becomes visible on GitHub only after a later Public Core publication.

## Allowlist boundary

The Public Core is defined by the versioned machine-readable manifest `public/public-core-v1.json` in the canonical repository. It uses an explicit **file-by-file allowlist** plus explicit source-to-destination mappings for public root metadata.

A new canonical file is private to the distribution by default: adding it to Forgejo does not publish it. Publication requires an intentional manifest change and successful contract tests.

The Public Core does not include canonical control or operations material such as:

- `.forgejo/**`;
- `Jenkinsfile`;
- canonical `.repository-standards.yml`;
- canonical `.repository-documentation.yml`;
- internal operations/runbook material;
- `integrations/siczb/**`;
- organization-specific CI, infrastructure, credential, or operational files that are not explicitly public contract material.

## Public root metadata

The GitHub root files `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, and `SUPPORT.md` are generated by copying intentionally public source files under `public/`. The public README is not a copy of the canonical internal README.

The public GitHub issue and pull-request templates are likewise sourced from `public/github/` and mapped into `.github/` in the generated distribution.

## Deterministic export

Canonical maintainers can assemble the Public Core locally from a qualified checkout with:

```bash
python3 tools/export_public_core.py \
  --source . \
  --target /tmp/repository-standards-public-core
```

The target must be empty. The exporter validates the complete plan before copying, copies only explicit allowlist entries, applies stable file/directory modes and timestamps, and validates the fully assembled output.

For identical source bytes and the same manifest, the exported file paths, bytes, and permissions are identical.

## Fail-closed safety checks

The exporter rejects at least:

- malformed or unversioned manifests;
- duplicate destination paths;
- absolute paths, `..`, path traversal, and backslash-based path ambiguity;
- source symlinks, including symlink escapes outside the canonical checkout;
- destination escapes outside the empty target;
- allowlisted paths that collide with forbidden destinations;
- unexpected or missing files in the assembled Public Core;
- a non-canonical or previous all-rights-reserved license;
- private-key, token, credential, and other high-confidence secret patterns;
- unapproved private host references and known private network references;
- non-UTF-8 files that cannot be security-scanned.

Known immutable historical schema identifiers that retain an original canonical URI require an explicit file-and-value exception in the manifest. Such exceptions are narrow and reviewed; they are not wildcard bypasses.

## License preflight

The Public Core uses one license: **Apache License 2.0** (`Apache-2.0`). The assembled `LICENSE` must match the canonical Apache License 2.0 text by SHA-256. A distribution containing the previous `All rights reserved` license cannot qualify.

## Publisher boundary

Public Core assembly and validation stop before any GitHub write. Authentication, GitHub push/release behavior, and publisher scheduling are separate downstream responsibilities. A valid local Public Core is therefore necessary but not sufficient for publication.
