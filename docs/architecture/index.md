# Architecture

## Purpose

The repository separates normative policy, machine-readable requirements, executable reference
state, generated consumer assets, and implementation-specific CI integration.

## Building blocks

- `standards/` contains immutable versioned specifications.
- `schemas/` describes ticket, repository, and artifact declarations that consumers can validate.
- `profiles/` contains machine-readable rules, compatibility pairings, profile requirements, and
  impact mappings.
- `reference/` contains golden repository skeletons, generated ticket templates, AI adapters, and
  versioned repository-declaration examples.
- `tools/` validates the repository and derives reference assets.
- `tests/` prevents drift between normative, machine-readable, generated, and published forms.
- `workboard` remains the external ticket-migration and dependency implementation.
- `maintenance` remains the external Jenkins Shared Library, artifact-provenance, bootstrap, and
  deployment-enforcement implementation.

## Contract flow

```text
versioned normative standards
          |
          v
machine-readable profiles + declaration schema + compatibility pairing
          |
          v
version-aware generators + reference declarations + artifact schemas
          |
          v
contract tests -> byte-for-byte legacy immutability + current consistency
          |
          v
released contract set -> explicitly migrated consumers
```

Implementations consume released artifacts. They do not fetch or reinterpret an unversioned branch
for every operation.

Published contract versions are immutable. A successor specification is additive: it receives its
own normative standard, profile or schema where applicable, and versioned references. Generated
assets may be shared between versions only while their generated bytes are identical; tests protect
that invariant.

## Runtime scenarios

Repository validation reads local standards, profiles, schemas, compatibility data, and reference
trees. Boilerplate rendering copies one reference profile into an empty destination and performs
only explicit substitutions.

Ticket Specification v1 asset rendering reads `profiles/ticket-specification-v1.json`. Ticket
Specification v2 asset rendering reads `profiles/ticket-specification-v2.json`. Both currently
produce the same six ticket-family templates because v2 changes lifecycle metadata rather than the
ticket-body structure. Each produces a version-specific AI adapter.

Ticket migration and dependency writes occur in Workboard rather than this repository. Lifecycle
automation, Jenkins/bootstrap enforcement, artifact-provenance generation, and deployment promotion
remain Maintenance responsibilities. Repository Standards publishes contracts but does not mutate
organization labels, consumer tickets, or deployed environments.

No runtime service or persistent datastore is required. Release tags are the durable distribution
boundary.

## Consumer-version boundary

Ticket Specification, Development Workflow, repository-declaration schemas, and opt-in web/deployment
standards are independently versioned but must be adopted as a supported contract set. The current
canonical machine-readable pairing matrix is
`profiles/repository-standards-compatibility-v2.json`. The published v1 compatibility profile remains
immutable for releases that reference it.

Currently supported sets are:

- declaration schema v1 + Ticket Specification v1 + Development Workflow v2 + Repository
  Documentation v1;
- declaration schema v2 + Ticket Specification v2 + Development Workflow v3 + Repository
  Documentation v1;
- declaration schema v3 + Ticket Specification v2 + Development Workflow v3 + Repository
  Documentation v1 + Web Application Baseline v1 + Deployment Environments v1.

Declaration v3 intentionally reuses Ticket Specification v2 and Development Workflow v3. Web and
deployment requirements are orthogonal to ticket lifecycle and branch workflow, so introducing them
does not justify a Development Workflow v4.

Unsupported combinations are rejected. A newly released contract set never migrates a repository
implicitly.

## Web application contract boundary

Web Application Baseline v1 owns user-visible requirements for explicitly adopting organization-owned
websites:

- stable `/impressum`, `/datenschutz`, and `/barrierefreiheit` routes;
- global internal navigation to those pages;
- visual/application-shell integration and alignment with the existing Design System decision;
- accessibility-statement structure and normal accessibility quality gates;
- public rendering of artifact provenance according to release state.

Application-specific legal content remains consumer-owned. Structural validation must not claim legal
compliance or invent missing facts.

The web profile references `schemas/artifact-provenance-v1.schema.json`. A final-release artifact may
retain detailed internal provenance while exposing only its release version publicly.

## Deployment contract boundary

Deployment Environments v1 separates source, artifact release state, and runtime environment. This
prevents branch or environment names from becoming implicit release semantics.

The default DEV source follows the existing branching model: `main` for `single` and `develop` for
`integration`. STAGE is optional. PROD accepts only an immutable final-release artifact. Promotion
selects an existing immutable artifact rather than rebuilding application content, and rollback
selects a previously released artifact.

The deployment standard does not change the Development Workflow rule governing build triggers or
manual release pull requests.

## Ticket Specification v2 adoption boundary

The standards-side v2 adoption contract exists with declaration schema v2 and Development Workflow
v3. Declaration schema v3 reuses the same lifecycle pair rather than redefining it.

Consumer repositories may adopt the v2 lifecycle only after every lifecycle writer they use supports
canonical `Status/Done` completion, explicit reopen transitions, and fail-safe
replacement-before-removal semantics. Workboard and Maintenance compatibility remains a separate
rollout concern. Canary validation is a precondition for enabling v2 lifecycle writes or blocking
enforcement in consumer repositories.

## Declaration v3 adoption boundary

Migration to declaration v3 is explicit and adds further preconditions beyond lifecycle readiness:

1. the consumer intentionally adopts the web and deployment standards;
2. the three required static routes contain current consumer-owned facts;
3. artifact-producing builds generate immutable provenance and release state;
4. deployment enforcement keeps source, artifact state, and environment independent;
5. PROD and rollback operate on immutable released artifacts;
6. the compatible Maintenance implementation passes the required Canary validation.

A consumer that cannot satisfy those conditions remains on its existing declaration. Publishing v3
does not make v1 or v2 invalid.

## Constraints

The repository MUST remain usable with Python's standard library. Project documentation and prompts
MUST NOT be centralized here. Compatibility with existing Maintenance and Workboard consumers MUST
be preserved during migration.

## Quality requirements

The design prioritizes one source of truth, reproducibility, offline validation, explicit
versioning, additive migration, immutable artifacts, idempotent automation, auditable writes, and
failure without destructive overwrites.
